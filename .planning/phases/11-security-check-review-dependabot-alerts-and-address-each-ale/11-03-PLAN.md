# Phase 11 Plan 03: web-version qs + on-headers Transitive Patch

## Meta
- **Phase:** 11
- **Plan:** 03
- **Requirements:** SEC-04, SEC-05, SEC-08
- **Depends on:** 11-02 (both plans modify web-version/package.json — must run sequentially)
- **Estimated complexity:** low

## Objective
Patch `qs` (alert #29 → `>=6.14.1`) and `on-headers` (alert #28 → `>=1.1.0`) in `web-version/package-lock.json` via `npm overrides` (SEC-04, SEC-05) without bumping parent packages (express / express-session). Preserve all server middleware behavior (SEC-08).

## Context
Pre-research confirmed both `qs` and `on-headers` are transitive in `web-version`, not direct deps. Typical parent chains:
- `qs`: `express → qs` (or `body-parser → qs`)
- `on-headers`: `express-session → on-headers`

Per D-01, we patch via `overrides` rather than bumping parents — bumping express or express-session is invasive and out of scope. Per D-02, after adding overrides we run `npm install` to regenerate the lockfile and verify with `npm audit`.

## Tasks

### Task 1: Confirm dep trees for qs and on-headers
**Type:** execute
**Files:**
- (read-only) `web-version/package.json`, `web-version/package-lock.json`

**Steps:**
1. Run `cd web-version && npm ls qs` — capture parent chain (expected: through express/body-parser/express-session)
2. Run `cd web-version && npm ls on-headers` — capture parent chain (expected: through express-session or compression)
3. Confirm current versions match `DEPENDABOT-ALERTS.md` baseline: `qs 6.13.0`, `on-headers 1.0.2`
4. If either is a direct dep (appears under top-level `dependencies` in `web-version/package.json`), STOP and surface to user — overrides may not be needed

**Verification:**
- [ ] `npm ls qs` shows current resolved version `6.13.0` and parent chain
- [ ] `npm ls on-headers` shows current resolved version `1.0.2` and parent chain
- [ ] Both confirmed transitive (not direct deps in `web-version/package.json`)

### Task 2: Add overrides for both packages and regenerate lockfile
**Type:** execute
**Files:**
- `web-version/package.json` — add overrides
- `web-version/package-lock.json` — regenerated

**Steps:**
1. Read `web-version/package.json`
2. Add top-level field (per D-01):
   ```json
   "overrides": {
     "qs": ">=6.14.1",
     "on-headers": ">=1.1.0"
   }
   ```
   If `overrides` already exists, merge both keys in
3. Run `cd web-version && npm install` — regenerates lockfile with overrides applied
4. Run `cd web-version && npm ls qs` — confirm `>=6.14.1`
5. Run `cd web-version && npm ls on-headers` — confirm `>=1.1.0`
6. Run `cd web-version && npm audit --json` — confirm zero findings for both packages (jq: `jq '.vulnerabilities.qs, .vulnerabilities."on-headers"'` returns `null` for both)

**Verification:**
- [ ] `web-version/package.json` contains `overrides.qs >=6.14.1` and `overrides.on-headers >=1.1.0`
- [ ] `npm ls qs` from `web-version/` shows `>=6.14.1`
- [ ] `npm ls on-headers` from `web-version/` shows `>=1.1.0`
- [ ] `npm audit` reports no findings for either package

### Task 3: Smoke test Express middleware behavior
**Type:** execute
**Files:**
- (read-only) `web-version/server.js`

**Steps:**
1. Determine server port: `grep -E 'PORT|listen' web-version/server.js | head -5` — use the port found (default likely 3000 or 5000)
2. Run `cd web-version && npm start` (or `node server.js`) and let it boot for 5 seconds
3. Run `curl -s -o /dev/null -w "%{http_code}\n" http://localhost:<PORT>/api/settings` (substitute port from step 1) — should return 200 or 401 (existing behavior); MUST NOT return 500
4. Run `curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:<PORT>/api/playlist/test-id/all` (substitute port) — should return existing behavior (any non-5xx is fine)
5. Kill the server

**Verification:**
- [ ] Server boots without errors
- [ ] Settings endpoint returns non-5xx (express-session + on-headers path works)
- [ ] No `qs` parser errors logged on startup
